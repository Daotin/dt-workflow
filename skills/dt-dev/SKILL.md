# AI 开发标准流程

只服务需要建档的重任务（跨会话 / 多文件 / 方案有分量）。轻量任务不进流程：对话里给方案、用户点头、直接干，零文件。

## 流程总览（单一来源）

完整流程以本节为准，其余阶段 skill（dt-dev-code / dt-dev-review / dt-dev-archive）只写自己阶段的操作细节。

```
初始化(.dt/) → 建任务目录 → 梳理与方案（Bug / 性能任务先复现；dt-think → design.md）
→ 【唯一硬门：用户确认 design.md】
→ 编码(dt-dev-code：拆清单 task.md → 执行)
→ Review(dt-dev-review)
→ 提交提议（用户同意才执行 git 操作）
→ 归档(dt-dev-archive：沉淀 spec.md → 记 progress.md → 目录移 done/)
```

## 初始化检查

每次运行先检查项目根目录是否存在 `.dt/` 目录，不存在则执行：

1. 创建以下结构：

```
.dt/
  spec.md
  progress.md      # 内容只写一行标题：# 进展记录
  tasks/done/
```

`spec.md` 模板：

```markdown
# 项目规范

> 开发任务开工前必读；归档时把新形成的约定 / 坑回写对应节。

## 架构和技术决策

## 开发规范

## 已验证的复用模式

## 踩坑和禁止方案

## 业务规则

## Review 必查项
```

2. 项目根目录的 CLAUDE.md（没有则创建）追加一行：`开发任务开工前先读 .dt/spec.md；收尾归档时把新的约定 / 坑回写进去。`
3. 检查 `.gitignore` 是否包含 `.dt/`，没有则追加。
4. 告知用户初始化完成。

## 遗留任务检查

`.dt/tasks/`（`done/` 之外）已有任务目录时，先提醒用户：该任务未收尾（未完成或未归档），问一句是续做、归档还是先放着，不默默开新档。

## 阶段一：梳理与建档

1. 读取 `.dt/spec.md`、`.dt/progress.md` 的近期条目和与需求相关的代码。项目知识已明确的内容不重复询问；需求与已有规则冲突时，先指出冲突。
2. 调用 `dt-think` 梳理需求与方案。Bug 或性能任务必须先建立能稳定出现用户所述问题的测试、命令或脚本，运行确认问题存在、记录基线并缩小复现场景，再用可验证的假设定位根因；无法复现时停下，说明已尝试的方式，并向用户索要环境、日志、HAR 等复现材料或临时诊断权限。用户确认方案前只允许新增复现测试、临时诊断脚本和诊断埋点，不得修改生产行为。
3. 任务目录在落盘时才创建：`.dt/tasks/<YYMMDD>-<英文slug>/`（如 `260726-algolia-search/`，slug 按梳理后确定的需求命名），落盘位置传 `<任务目录>/design.md`。design.md 必含章节：一句话结论 / 背景（含需求边界与调研结论）/ 方案（含权衡：为什么不选另一条路）/ 影响范围 / 风险 / 验收标准（每条附验证方式）。Bug 或性能任务还要在背景中记录复现方式、实际结果和根因证据。不写 prd.md，需求内容并入 design.md。

## 阶段二：等待确认（唯一硬门）

design.md 写好后告知用户：

"方案已写入 `<任务目录>/design.md`，确认后进入编码阶段；也可以提出修改意见。"

除阶段一允许的复现和诊断操作外，用户确认前不得编码、不得创建 task.md。用户提修改意见 → 改 design.md 后再次确认。确认通过后，在 design.md 标题下加一行 `> 状态：已确认 <YYYY-MM-DD>`，再进入阶段三。

## 阶段三：编码、Review 与归档

用户确认后调用 `dt-dev-code`：它拆解执行清单并逐项实现，完成后自动调用 dt-dev-review，Review 后提议提交（用户同意才执行），再调用 dt-dev-archive。

## 中途升档

对话中没建档的任务变大时（一次会话干不完 / 方案值得留档），可直接进入本流程：建任务目录，把对话中已确认的内容整理进 design.md，从阶段二继续，前面聊的不浪费。
