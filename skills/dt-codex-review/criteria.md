# 方案评审判据

Codex 评审、Claude 复核共用这一份判据，其他地方只引用，不复制条目。

## 只报会影响大方向的问题

| # | 类型 | 要回答的问题 |
|---|---|---|
| 1 | 需求理解 | 方案解决的是不是需求真正要解决的问题？有没有理解偏、漏掉需求里的关键场景？ |
| 2 | 架构与选型 | 整体思路、技术选型、模块划分合不合适？有没有明显更简单或更稳的路线被漏掉？ |
| 3 | 与现有架构冲突 | 和项目现有的分层、数据流、约定、已有模块是否冲突？会不会重复造一套已有的能力？ |
| 4 | 主流程回归 | 方案落地后，现有核心主流程会不会出 bug、行为变了、老数据或老调用方用不了？ |
| 5 | 关键环节缺失 | 有没有漏掉不补就要返工的环节：兼容、数据迁移、上线与回退、并发与重复执行、权限？ |
| 6 | 可行性 | 方案依赖的接口、字段、能力、第三方行为是否真的存在、真的这样工作？ |

## 不报

- 命名、措辞、文档排版。
- 代码写法、实现细节、编码时再定也来得及的细节。
- 性能微调、优化建议、"可以更好"。
- 测试怎么补、日志怎么加这类不影响方案走向的内容。
- 这次需求之前就存在的问题：可以单独标「原有问题」列出，但不要求本次修改。

## 每条意见的硬要求

- 写清「不改会出什么后果」：具体到哪个流程、哪类用户或数据会出什么问题。写不出后果的不算重要问题，不报。
- 给出依据：方案里的章节，加上代码里的 `文件:行号` 或文档出处。凭名字猜测的不算依据。
- 同一类问题合并成一条，列出所有出现位置。
