# 需求梳理

用户不看需求原文。本 skill 替用户把链接里的全部资料读完、整理好，用大白话讲清要做什么，讨论清楚后产出 PRD.md，交给 dt-dev。

<HARD-GATE>
只读外部系统：不改飞书项目工单、不改飞书文档、不评论、不流转节点、不发消息。不写业务代码，不出技术方案（技术方案是 dt-dev → dt-think 的事）。只往本需求的目录 `~/.dt/reqs/<工单号>-<英文短名>/` 写文件。
</HARD-GATE>

## 存放位置

一个需求一个目录，不放进具体项目：

```
~/.dt/reqs/<工单号>-<英文短名>/      # 例：6992980656-zh-listing-pricing/
  raw/        # 原始材料，每份一个文件（不进 git）
  PRD.md      # 梳理后的最终版，只给用户看
```

- 拿到链接时用户往往还不知道在哪个项目做，全栈需求还会跨几个仓库，所以需求材料按需求存，不按项目存。
- 飞书文档 PRD 没有工单号时，用文档 token 代替工单号。
- 目录已存在说明以前梳理过：先读已有的 PRD.md 和 raw/，问用户是接着讨论还是重新拉取。
- `~/.dt/.gitignore` 已忽略 `reqs/*/raw/`，只有 PRD.md 进 git，不自动提交。

## 流程

### 1. 先问角色

开工第一句问用户：这个需求这次做前端，还是全栈。讲解重点和任务拆分都按这个来。问完不等回答，先做第 2、3 步（读材料不依赖答案），到第 4 步讲解前拿到答案。

### 2. 读全部材料

**飞书项目工单**（`project.feishu.cn/.../story/detail/<id>`），用 meegle skill：

1. `meegle url decode --url '<链接>'` 拿 `simple_name`、`work_item_id`；`meegle project search --project-key <simple_name>` 换成 `project_key`。
2. `meegle workitem get --project-key <key> --work-item-id <id> --fields '["_all"]' --params '{"page_size":200}'`，有 `next_page_token` 就带 `--params '{"page_size":200,"page_token":"<token>"}'` 翻页。字段有几百个，大部分是流程状态，只取下面这些（按字段名找，key 各空间不同）：
   - 名称、需求工单描述、AI 总结需求、PRD 文档、AI 内审报告、AI GenAI 判定
   - 优先级、规划迭代、需求所属项目、功能模块/子系统、需求颗粒度
   - 需要前端开发、需要后端开发、角色成员（产品经理、PO、前端、后端、测试）
   - 工单自带的「描述」常为空，真正的描述在「需求工单描述」
3. `meegle comment list --project-key <key> --work-item-id <id>` 读评论。
4. 有附件字段就按 meegle 的附件协议下载。

**飞书文档 PRD**（工单「PRD 文档」字段里的链接，或用户直接给的），用 lark-doc skill：

1. `lark-cli docs +fetch --as user --doc '<链接>'` 读正文，存 `raw/prd.xml`。
2. 正文里每个 `<img src="...">` 都用 `lark-cli docs +media-download --as user --token <src> --output raw/img/<src>` 下载，再逐张打开看。`alt` 是飞书自动生成的图注，只当线索，以看到的图片为准。
3. 嵌入的表格、多维表格、画板，按 lark-doc 的路由表切到对应 skill 读。

**链接逐个打开**：工单和 PRD 里出现的每个链接都要读，一层就够，不顺着子链接无限展开。

- 飞书文档、知识库：同上走 lark-doc / lark-wiki。
- Figma 设计稿：用 Figma MCP 读页面截图和设计信息（调 `get_design_context` 前按要求先加载 figma-design-to-code skill）。
- feishuapp 设计页（如 `shoplazza.feishuapp.com/.../studio-app/.../pages/xxx.html`，会附样式代码和 Figma 地址）：用 ego-browser 打开，读页面文字、截图，取出样式代码和里面的 Figma 地址再读 Figma。
- forge AI 审核报告（工单「AI 内审报告」字段里的 `forge.shoplazza.site/#/spaces/<空间>/prd-tickets/<id>` 链接）：用 ego-browser 打开读正文。打不开（提示"工单不存在或没有权限"）就用工单字段里的摘要，讲解时明确说"只看到摘要，没看到全文"。

每份材料存一个文件到 `raw/`，文件名能看出是什么。读不到的（没权限、链接失效）记进清单，不猜内容。

### 3. 和工作知识库对照

读完材料后，每次都按 `~/.dt/work-knowledge/index.md` 的查库规则，查和这个需求相关的内容（同一个平台、同一个模块、同类字段的讨论结论、以前的坑），拿需求逐条对照：

- **冲突**：需求的说法和库里的结论对不上（比如 PRD 说某个字段现在不显示，库里记的是已经显示；PRD 要的做法库里记过行不通）。列进第 4 步的"需要找产品确认的问题"，写清需求怎么说、库里怎么说、库里那条的出处和日期。
- **补充**：库里有、PRD 没提但会影响这个需求的信息（相关限制、依赖的服务、以前踩过的坑）。写进讲解对应的功能下面，标出处。
- 库里的内容按它标注的可信度用：只当线索的，讲的时候说明"库里记的，未核实"；冲突不替产品裁定。

同时查出这个需求要改哪些仓库，第 6 步写进 PRD.md。

### 4. 讲解

固定格式，大白话，用需求里的真实字段名和页面名举例：

1. **一句话**：这是什么需求
2. **为什么要做**：现在有什么问题，影响谁
3. **涉及哪些页面和字段**：按页面或模块列，对照截图、设计稿讲清每个功能做什么、怎么操作
4. **工单信息**：优先级、迭代、产品经理、需要前端/后端
5. **需要找产品确认的问题**：PRD 没写清、前后矛盾、和工单描述对不上、和工作知识库冲突的地方，编号列出；AI 审核报告里的 P0、P1 合并进来
6. **没读到的材料**：清单，没有就不写

竞品不单列一节。只有第 5 项里某个问题需要参考答案时，才按 `~/.dt/verify-channels.md` 渠道 4 查这一个问题，把竞品做法写在这个问题下面，带出处。

讲完停住，等用户提问。

### 5. 讨论

用户提问驱动：问什么答什么，需要查的先查再答。讨论出的结论、用户找产品确认回来的答案，当场记下，第 6 步写进 PRD.md。

### 6. 写 PRD.md

用户说"可以了""写 PRD"时写，章节固定：

```markdown
# <需求名>

> 来源：<工单链接> ｜ PRD：<PRD 链接> ｜ 梳理日期：<YYYY-MM-DD>

## 一句话
## 背景
## 要做的功能
（按页面/模块，每条写清做什么、规则和边界）
## 不做的
## 已确认的问题
（问题 → 结论 → 谁确认的）
## 还没确认的问题
## 涉及项目
（每个项目一行：仓库路径、改什么）
## 任务清单
（按用户的角色拆：前端 / 后端 / 联调自测）
```

只写讨论确认过的内容，不写过程。写完告诉用户路径。

### 7. 交给 dt-dev

告诉用户：到「涉及项目」里的项目开窗口，说"用 dt-dev 做 <工单号>"。dt-dev 会读这份 PRD.md 当需求输入，直接进技术方案。全栈需求每个项目各走一次 dt-dev，都引用同一份 PRD.md。

## 边界

- 不改 PRD 和工单，发现 PRD 有问题只列进"需要找产品确认的问题"，由用户去找产品。
- 不替产品决定做不做、怎么做。
- 用户纠正的做法按全局规则「工作知识库」一节入库。
