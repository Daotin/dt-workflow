# AI Review

## 前置检查

项目根目录存在 `.dt/` 时走下方完整流程；不存在时不拒绝也不初始化，跳过任务档案和 spec 相关步骤，按通用检查执行（只输出，不落盘）。

## 流程

1. 定位任务目录：`.dt/tasks/`（`done/` 之外）只有一个就用它，多个列出让用户选；读取其中的 `design.md`（需求、验收标准、技术方案）和 `task.md`（执行清单）。项目里没有任何任务、或用户只要求通用检查时，跳过本步，后面只按 spec 和通用检查项审查。
2. 读取 `.dt/spec.md`，重点看「Review 必查项」节。
3. 确定审查范围：用 `git status` 和 `git diff` 圈出本次任务改动的文件，只审这些；用户明确要求时才扩大范围。design.md 有「涉及仓库」节时，逐个仓库进目录跑 `git status` 和 `git diff`，合起来作为审查范围，下面说的 git diff 都指这份合集；第 5 步的 lint 和测试也逐个仓库跑。
4. 执行双视角审查。有任务档案时两个视角同时进行，各自用干净的上下文，避免功能判断和代码质量互相干扰：
   - 共同规则：给路径不给转述；自己读取指定文件和 git diff；task.md 的勾选和"已完成"都未经证实；只回报问题清单，每条附文件:行号和依据，不改代码。
   - 问题分级：每条标一个级别——「必须改」（本次改动引入、影响正确性，写得出触发步骤：什么输入或操作、走到哪段代码、出现什么错误结果，而且不需要多个少见条件同时成立）、「建议」（影响正确性，但写不出触发步骤，或要多个少见条件同时成立才会出现）、「小问题」（不影响正确性、但违反 spec.md 或项目规范，纯风格不报，最多列 3 条）、「原有问题」（用 git blame 确认不是本次改动引入的）。同一类问题合并成一条，列出所有出现位置，让作者一次改完。
   - **功能符合性（默认由 Codex 审）**：读取 `design.md`、`task.md` 和 git diff，逐条检查需求、方案和验收标准是否完整且正确实现，有没有遗漏、只做一半、实现错误或超出范围的行为。运行方式见下方「功能符合性由 Codex 审」。
   - **代码质量（子代理）**：读取 `.dt/spec.md` 相关节（重点「Review 必查项」「踩坑和禁止方案」）和 git diff，检查架构、业务规则、开发规范，并按 `~/.agents/skills/dt-think/checklist.md` 逐条检查。
   - 两个视角并行执行，结果按「功能符合性」「代码质量」分开保留，不互相合并或抵消。
   - 子代理不可用时，本该由子代理做的视角改由主对话分开自审；没有任务档案时始终跳过功能符合性（不调用 Codex），只做代码质量审查。
5. 运行 lint、类型检查和相关测试，项目没有配置的跳过并在摘要中注明，不安装新工具。有任务档案时，再逐条执行 design.md 验收标准里写的验证方式并记录结果，执行不了的写"未验证"。
6. 核实审查回报的问题，不认同的不静默丢弃，在摘要中说明理由。按级别处理：「必须改」能安全修复的直接修复；「小问题」能安全顺手改的就改；「建议」和「原有问题」不改，在摘要里分别列出。修复后重跑相关验证，再复审：
   - 谁提的问题谁复审：Codex 提的仍交给 Codex，子代理提的仍交给子代理。
   - 只审修复产生的新 diff，不重审整份改动；只看原问题是否真修好、新 diff 有没有引入新问题。
   - 已报过的问题（包括已修复的、已说明不认同的）不再重复报。
   - 首轮审查加复审最多 3 轮。第 3 轮后仍有「必须改」，停止循环，结论记为「审查未通过」：在摘要里列出剩余问题，说明是否需要回头改方案，然后停下，等用户决定继续修、回头改方案，还是接受风险放行。
7. 输出简洁 Review 摘要。第一行先写结论「审查通过」或「审查未通过」，再写数量：必须改 X、建议 W、小问题 Y、原有问题 Z，共审 N 轮；没有要改的问题就直接写"没有需要修改的问题"。有任务档案时按「功能符合性」「代码质量」分别列出通过项、问题项和已修复项，「功能符合性」标题后写明这次由谁审（Codex，或子代理及原因）；没有任务档案时只输出代码质量摘要。任务 Review 同时写入 `<任务目录>/review.md`，无任务的通用检查只输出、不落盘。

## Codex 配置

- 模型：`gpt-6.2-sol`
- 推理档位：`xhigh`

代码审查用的模型和档位只改这里（dt-codex-review 的方案评审另有一份）。

## 功能符合性由 Codex 审

功能符合性换一个模型（Codex）来审，避免写代码的模型审不出自己的遗漏。

先决定这次用不用 Codex：

- 用户说这次不用 Codex，或 `command -v codex` 找不到命令：功能符合性改派干净上下文的子代理，检查内容不变，并在摘要里写明原因。
- 其余情况都用 Codex。

Codex 每运行一轮（首轮，以及第 6 步里 Codex 提的问题被修复后的复审）：

1. 输出目录是 `<任务目录>/code-review/`。目录里已有 `round-N-codex.md` 的最大 N 加 1，就是本轮的 N。
2. 把审查范围内各仓库此刻 `git diff` 的输出存为 `round-N-reviewed.diff`（多个仓库时每段前写上仓库路径），留给下一轮对比修复前后的差异。未跟踪的新文件不在 `git diff` 里，逐个用 `git diff --no-index /dev/null <文件>` 把内容追加进去（文件有内容时这条命令的退出码是 1，属正常）。
3. 写提示词 `round-N-prompt.md`，包含：
   - 身份和限制：你是代码审查人，只能读，不要修改任何文件；用中文输出；没有问题就直接说没有，不为凑数降低标准。
   - 第 4 步「共同规则」「问题分级」和功能符合性检查内容的原文。
   - 路径：`design.md`、`task.md` 的绝对路径；审查范围内每个仓库的绝对路径；第 3 步圈出的改动文件清单（含未跟踪的新文件），让它自己在各仓库跑 `git status` 和 `git diff`。
   - 复审轮再加：本轮修复对应的问题编号和改动位置（文件:行号）；上一轮和本轮两份快照 `round-(N-1)-reviewed.diff`、`round-N-reviewed.diff` 的绝对路径，让它对比这两份文件，找出修复产生的全部改动（包括被删掉的内容）；之前各轮 `round-*-codex.md` 的绝对路径；写明只看这些修复有没有真修好、有没有引入新问题，已报过的问题不再报。
4. 后台运行，等结束通知，不轮询；首轮时代码质量子代理和它同时跑：

   ```bash
   codex exec -m <模型> -c model_reasoning_effort="<档位>" -s read-only -C <主仓库目录> --skip-git-repo-check --ephemeral -o <输出目录>/round-N-codex.md - < <输出目录>/round-N-prompt.md
   ```

5. 退出码不为 0，或 `round-N-codex.md` 不存在、为空：把报错原文告诉用户，停下等用户决定，不自动改派子代理，也不拿上一轮结果代替。
6. Codex 的意见和子代理的意见一样，进入第 6 步由主对话逐条核实，不因为是 Codex 提的就默认对。
